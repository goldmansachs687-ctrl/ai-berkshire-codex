# 伯克希尔＋AIVA 联合模式

本联合默认来自用户明确要求两个插件一起作用；默认调用提示也明确写明伯克希尔＋AIVA。仅在该联合选择或用户明确联用授权范围内加载显式入口模块，其他插件不因此获得隐式调用许可。用户2026-11-07另行要求链接估值工具，按[估值工具层](valuation-tools.md)明确选择FinanceToolkit、company-valuation及专业插件；该授权限定在本次研究需要的建模/复核支援，不扩大交易或账户权限。

完整公司研究默认使用本模式；用户明确“只用原伯克希尔”或“只用AIVA”时服从选择。专项取数、公司信息、插件问答不升级为完整团队。恢复已有研究时先检查断点，只补本次授权的缺口，不为启用联合模式重跑已完成工作。

## 唯一主流程与真实依赖

由 `berkshire-team` 唯一调度，沿用它的长桥等取数、资料库、研究目录、run.json、四角色、质询、模型与独立复核。AIVA 为同一研究增加分析和表达标准。不能再启动 AIVA 的 investment-team，也不能经 aiva 入口递归转回主入口。

1. 从当前会话可用技能/插件信息找到已启用的 `ai-value-investing-agents` 插件。必须定位其随包的 `skills/investment-memo-craft/SKILL.md`，不能用全局同名技能或本页概述冒充读过AIVA。
2. 宿主未给出实际路径时，使用支持的只读命令 `codex plugin list --marketplace berkshire-community --json`。在 installed 数组中按 name 精确匹配 `ai-value-investing-agents`，要求 installed、enabled 均为 true。对 local source，可使用实际返回的 source.path；核对根 plugin.json 的 name/version 与安装记录相同，再读取 UPSTREAM.json 和上述技能全文。禁止猜测家目录、缓存版本或执行外部安装脚本。
3. 保存所读模块的真实绝对路径、SHA256、插件版本、上游提交和读取时间至本次目录 `joint-mode.json`。该文件是方法使用记录，不是财务事实证据，不写入 evidence.json 充数。插件源目录是只读依赖，不在研究过程中改写。
4. 不可定位、未启用、版本不符或读取失败时明确“AIVA未加载，当前只运行伯克希尔”，记录原因并继续本已授权的主流程；不自动安装、启用插件，不假称联合完成。用户明确只接受联合模式时，先完成可独立保留的取证，保留联合部分待办。

## 在同一团队内应用

读完真实AIVA模块后，主代理将以下对应标准及模块路径随任务交给原四角色。共享的是问题和标准，不是预设看多/看空结论；不重复抓取已验证的同一事实。

| 角色 | AIVA补强内容 | 必须落到的底稿 |
| --- | --- | --- |
| 商业模式与护城河 | 先画收入/成本/再投资机制；用一句话解释谁付钱及为何重复；护城河过去五年的变化与可推翻证据 | business.md 的经营机制及护城河段落 |
| 财务与估值 | 找出驱动股东现金的两三个变量；反向DCF检验现价隐含预期；用证据或价格界定结论改变条件 | financial.md、共享模型与对应计算记录 |
| 行业与竞争 | 把行业增长与公司获利分开；解释产业链位置、利润池、定价和资本强度怎样影响价值捕获 | industry.md 的利润池及竞争验证 |
| 风险与管理层 | 写出有说服力的最强不买理由和自己的潜在误判；用并购、回购、激励等实际行为评价管理层 | risk.md 的反证及资本配置记录 |

这里是对已读取模块的任务映射，不是另造一个AIVA团队。确需管理层等纵深模块时只读取相关标准、分配给现有责任角色，不重开完整工作流。

## 规则冲突时的取舍

- 用户/工作区要求优先。本插件默认正文顺序为：①公司基本信息与发展史；②商业模式；③十年财务汇总及十至二十年原始财报入口；④商业质量、护城河、文化和管理层实际行为；⑤多方法估值与取舍；⑥最后参考外部投行。AIVA的英文、三至五年及十一节模板不覆盖这些要求。数据不足时明确实际覆盖，不伪造十年表。
- Wiki正文为背景/历史入口，长桥及现有授权财务工具供基础数据，关键事实按需补官方披露；沿用主插件来源、日期、单位、累计值和独立双源定义。
- 唯一有效证据表和估值口径由主插件维护。保留利润到归母可分配现金桥、SBC/租赁/净现金处理和行业适配；多方法用于交叉检验，解释取舍，不机械平均。不能导入固定折价、固定倍数或因目标价不同换模型。
- 核验必须使用主插件 evidence_gate.py / report_audit.py，保留 PASS/FAIL/INCOMPLETE；不能用AIVA的其他审计结果抵消主插件FAIL或缺失，也不把写作评分称财务核验。
- 不因AIVA提到持仓、行动区或组合管理就推断用户仓位、提供已授权交易或读取账户；需要决策表时放在估值证据之后，实际持仓未知则只给条件。

## 交付前应用、复核与恢复

四角色分析、质询、独立估值先完成并落盘，再用AIVA原模块整理报告：机制与数字支撑明确判断、清晰解释分歧、克制排版，审计细节移附录。编辑不能擅自改事实/模型输入；若需要改变，回到责任底稿和模型同步核对。外部投行放最后，区分全文/摘要/评级行动。

估值工具层先完成计算、模型检查及差异修复，再交AIVA编辑；实际工具执行记录单列valuation-tools.json。AIVA编辑必须发生在最终核验和独立复核之前。复核者检查最终报告及模型；后续实质改动须重核受影响结论并更新文件哈希，不能沿用编辑前的复核标签。

`joint-mode.json` 至少含：mode、orchestrator、AIVA插件身份/版本/上游提交、module_path、module_sha256、loaded_at、status，以及applications数组。刚读完只能写 status=loaded；applications逐项记录角色、标准、实际文件与段落、applied或unresolved、限制。只有实际应用并写明位置的条目才算applied；最终有未决项写partial，不能按清单自动全勾。正文或交付简述实际采用的补强及缺口，并链接该记录。

恢复研究须重读joint-mode.json并核对模块哈希。上游模块变化不自动推翻旧研究或重跑四角色；保留原应用记录，只对本次要求涉及的变化增量处理。原本没有此文件的旧报告不补造联合调用历史。
